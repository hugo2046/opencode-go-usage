**日期：** 2026-09-16

这个插件有**四条静默失败路径**（没有密钥、没有 Go 套餐、密钥失效、插件没加载），全都表现成同一件事：侧栏里没有 `OpenCode Go` 小节，而且不报错。这是刻意设计——没有 Go 套餐的人不该看到一个报错的小节——但代价是"看不到"这个症状本身不告诉你原因。

## 先跑这一条：数据层诊断

**看不到小节时，第一件事是把 TUI 排除在外。** 插件分成两层：`usage.ts`（纯逻辑，无 TUI 依赖）和 `tui.tsx`（渲染）。第一层可以脱离 opencode 单独跑，所以一条命令就能告诉你问题在数据层还是渲染层。

```bash
cat > /tmp/ocgo-diag.ts <<'EOF'
const repo = process.env.REPO
if (!repo) { console.error("请先 export REPO=<仓库绝对路径>"); process.exit(2) }
const { defaultStateDir, resolveKey, fetchUsage, ROWS, formatBar, formatPercent, formatCountdown } =
  await import(`${repo}/usage.ts`)

const dir = defaultStateDir()
const key = resolveKey(dir)
console.log("stateDir:", dir)
console.log("key:", key ? `found (len=${key.length})` : "NOT FOUND")
if (!key) process.exit(1)

const snap = await fetchUsage(key)
console.log("snapshot.kind:", snap.kind)
if (snap.kind !== "ok") {
  console.log("message:", snap.message)
  process.exit(1)
}
for (const row of ROWS) {
  const w = snap.usage[row.key]
  console.log(`${row.label.padEnd(6)} ${formatPercent(w.percent, w.status)} ${formatBar(w.percent)} ${formatCountdown(w.resetsAt)}`)
}
EOF

REPO="$HOME/workspace/opencode-go-usage" bun run /tmp/ocgo-diag.ts
```

仓库不在那个位置就改 `REPO` 的值。脚本本身不含任何硬编码路径，可以原样复制。

> 脚本用 `defaultStateDir()`（opencode 的 data 目录，`auth.json` 真实位置），这与插件的首选候选目录一致。插件在 TUI 里还会把 `api.state.path.state` 作为次选，但那是 state 目录、通常没有 `auth.json`，所以两边结论一致。

一切正常时的输出（数字会不同）：

```
stateDir: /Users/你/.local/share/opencode
key: found (len=67)
snapshot.kind: ok
5 小时用量   1% ░░░░░░░░░░░░░░░░░░░░ 重置于 1 小时 46 分钟
每周用量    55% ███████████░░░░░░░░░ 重置于 4 天 12 小时
每月用量    27% █████░░░░░░░░░░░░░░░ 重置于 27 天 20 小时
```

怎么读这个输出：

| 输出 | 含义 | 去哪 |
|---|---|---|
| `key: NOT FOUND` | 密钥解析失败 | [§1.2](#12-没有密钥) |
| `snapshot.kind: dead` | 无 Go 套餐或密钥失效 | [§1.3](#13-无-go-套餐或密钥失效) |
| `snapshot.kind: soft-error` | 网络或上游问题 | [§3](#3-标题带感叹号) |
| 三行都正常打出来了 | **数据层完好，问题在渲染层或插件加载** | [§1.1](#11-插件没加载) |

最后一种情况最常见：数据层没问题，插件根本没被 opencode 加载。

## 1. 侧栏完全没有 `OpenCode Go` 小节

按下面顺序排查。上面那条诊断命令已经把 1.2 和 1.3 区分开了；如果它三行正常，直接看 1.1。

### 1.1 插件没加载

这是最常见的原因，而且有三种具体形态。

**检查注册文件存在且内容正确：**

```bash
cat ~/.config/opencode/tui.json
```

期望输出：

```jsonc
{
  "$schema": "https://opencode.ai/tui.json",
  "plugin": ["/绝对路径/opencode-go-usage/tui.tsx"]
}
```

三个典型错误：

| 错误 | 症状 | 修法 |
|---|---|---|
| 文件不存在 | 插件从未被加载 | 按 [安装指南](安装指南_20260916.md) 创建它 |
| 写进了 `opencode.json` / `opencode.jsonc` | 插件被 loader 拒绝 | `opencode.json` 只加载 **server 端**插件；TUI 插件必须在 `tui.json` 里。从 `opencode.json` 的 `plugin` 数组里删掉本插件，加到 `tui.json` |
| 路径是相对路径或写错了 | 加载失败 | `plugin` 数组里必须是 `tui.tsx` 的**绝对路径**。用 `ls` 确认那个路径真的存在 |

**确认路径真的指向文件：**

```bash
ls -l "$(python3 -c "import json,pathlib;print(json.loads(pathlib.Path.home().joinpath('.config/opencode/tui.json').read_text())['plugin'][0])")"
```

**检查 opencode 版本：**

```bash
opencode --version
```

需要 **1.18.30 或更高**。这套 TUI 插件 API 没有公开文档，已在 1.18.30 与 1.18.31 上实测通过（两版的内置 sidebar 插件 id 与三个 slot 名都一致）。更低的版本可能根本没有 `slots.register` 或 `sidebar_content`。

**确认重启了：** `tui.json` 只在 opencode 启动时读取。改完必须完全退出再开，不是新建一个会话。

**还是定不下来？用探针插件。** 这是唯一能区分"loader 没加载"和"加载了但内部逻辑失败"的手段——插件内部的错误走 `console.error`，在 TUI 里会被吞掉，日志里什么都看不到。

装一个只写文件的最小插件：

```bash
cat > /tmp/ocgo-probe.tsx <<'EOF'
/** @jsxImportSource @opentui/solid */
import type { TuiPlugin, TuiPluginModule } from "@opencode-ai/plugin/tui"
import { appendFileSync } from "node:fs"

const log = (m: string) => {
  try { appendFileSync("/tmp/ocgo-probe.log", `${new Date().toISOString()} ${m}\n`) } catch {}
}

const tui: TuiPlugin = async (api) => {
  log("tui() called")
  log(`state.path = ${JSON.stringify(api.state?.path)}`)
  try {
    const ret = api.slots.register({ order: 350, slots: { sidebar_content: () => null } })
    log(`slots.register returned: ${JSON.stringify(ret)}`)
  } catch (e) {
    log(`slots.register THREW: ${e instanceof Error ? e.message : String(e)}`)
  }
  log(`plugins.list() = ${JSON.stringify(api.plugins?.list?.())}`)
}

const plugin: TuiPluginModule & { id: string } = { id: "ocgo-probe", tui }
export default plugin
EOF

# 临时加进 tui.json（先备份）
cp ~/.config/opencode/tui.json /tmp/tui.json.bak
python3 -c "
import json, pathlib
p = pathlib.Path.home()/'.config/opencode/tui.json'
cfg = json.loads(p.read_text())
if '/tmp/ocgo-probe.tsx' not in cfg['plugin']: cfg['plugin'].append('/tmp/ocgo-probe.tsx')
p.write_text(json.dumps(cfg, indent=2) + '\n')
"
rm -f /tmp/ocgo-probe.log
```

重启 opencode，然后：

```bash
cat /tmp/ocgo-probe.log
```

怎么读：

| 结果 | 结论 |
|---|---|
| 文件不存在 | **loader 根本没加载插件** — 回到上面查 `tui.json` 路径与 opencode 版本 |
| 有 `tui() called` 但没有 `slots.register returned` | 注册抛错了，看那行 `THREW` 的消息 |
| 有 `slots.register returned: "ocgo-probe"` | **加载与注册都正常**，问题在你自己插件的渲染逻辑或数据获取 |
| `plugins.list()` 里能看到 `opencode-go-usage` 且 `active: true` | 本插件确实被加载了 |

`state.path` 那行尤其有用：它打出宿主实际给的四个路径（`home` / `state` / `config` / `worktree`），能直接看出插件在哪个目录找 `auth.json`。本插件早期就是因为把 `state` 目录当成了 `auth.json` 所在的 data 目录，导致密钥永远找不到、整节永不渲染——`bun test` 全绿也抓不到，只有这个探针能看见。

用完恢复：

```bash
cp /tmp/tui.json.bak ~/.config/opencode/tui.json && rm -f /tmp/ocgo-probe.tsx /tmp/ocgo-probe.log
```

### 1.2 没有密钥

诊断命令输出 `key: NOT FOUND` 时。

密钥按两级优先级解析（详见 [配置与行为契约 §2](配置与行为契约_20260916.md#2-密钥解析)）：

```bash
# 1. 环境变量优先
echo "${OPENCODE_GO_API_KEY:+已设置（值不打印）}"

# 2. 其次是 opencode 自己的 auth.json
python3 -c "
import json,pathlib
p = pathlib.Path.home()/'.local/share/opencode/auth.json'
d = json.loads(p.read_text())
print('providers:', list(d.keys()))
print('opencode-go 存在:', 'opencode-go' in d)
"
```

期望 `providers` 列表里有 `opencode-go`。

| 情况 | 修法 |
|---|---|
| `auth.json` 里没有 `opencode-go` | 跑 `opencode auth login` 登录 OpenCode Go，或设置环境变量 `OPENCODE_GO_API_KEY` |
| 键名被改过（比如测试时改成了 `opencode-go-bak`） | 改回 `opencode-go` |
| 密钥值是空字符串或纯空格 | 纯空白视为没有密钥。重新登录 |
| `auth.json` JSON 损坏 | 插件会静默退化为"没有密钥"。修复 JSON 或重新登录 |

改完**不需要重启** opencode：密钥在每次刷新时惰性解析，下一次 `session.idle` 或 5 分钟兜底刷新就会拾取。

### 1.3 无 Go 套餐或密钥失效

诊断命令输出 `snapshot.kind: dead` 时。看它打出的 `message`：

| message 含 | 含义 | 修法 |
|---|---|---|
| `subscription required` / `EntitlementError` | 这个密钥对应的账号**没有生效的 Go 套餐** | 确认套餐状态，或换一个有订阅的账号的密钥 |
| `HTTP 401` / `HTTP 403` | 密钥无效、已撤销、或无权访问 | 重新 `opencode auth login` 换新密钥 |

**`dead` 是闩锁。** 命中一次后插件永久停止请求，连 5 分钟兜底刷新也不再发。换好密钥后**必须重启 opencode** 才会恢复——这一点和 1.2 不同。

用 curl 直接确认（不经过插件）：

```bash
KEY=$(python3 -c "import json,pathlib;print(json.loads(pathlib.Path.home().joinpath('.local/share/opencode/auth.json').read_text())['opencode-go']['key'])")
curl -s -o /dev/null -w "HTTP %{http_code}\n" -H "authorization: Bearer $KEY" https://opencode.ai/zen/go/v1/usage
```

`HTTP 200` = 密钥和套餐都没问题。`HTTP 401`/`403` = 密钥问题。

> 别把密钥值贴进聊天、日志或 issue。上面的命令刻意只打状态码。

## 2. 小节位置不对

`sidebar_content` 是叠加模式，各插件按 `order` 升序排。本插件用 `order: 350`。

| 你看到的 | 原因 | 修法 |
|---|---|---|
| 额度在 `MCP` 或 `LSP` **之前** | `order` 太小。`internal:sidebar-context` 就是 100，同档时外部插件排它后面但仍在 MCP 前 | 把 `tui.tsx` 的 `order` 调到 300 以上 |
| 额度被 `Todo` / `Files` 挤到下面，你希望它在上面 | 当前 350 就在 Todo(400) 之前，检查是否被改过 | 确认 `tui.tsx` 的 `api.slots.register` 里是 `order: 350` |
| 你希望额度沉到侧栏**最底** | 350 落在 Todo/Files 之前 | 改成 `order: 600` |

内置 order 表（从 opencode 1.18.30 二进制解出）：

| 插件 id | order |
|---|---|
| `internal:sidebar-context` | 100 |
| `internal:sidebar-mcp` | 200 |
| `internal:sidebar-lsp` | 300 |
| `internal:sidebar-todo` | 400 |
| `internal:sidebar-files` | 500 |

改 `order` 后要重启 opencode。

**如果宿主升级后位置又乱了**，说明 opencode 调整了内置 order。这是与宿主的隐式契约，升级后需要重新确认。

能用一条命令做到的是**列出内置 sidebar 插件的 id**，看看有没有新增或改名：

```bash
strings -a "$(readlink -f "$(which opencode)")" | grep -oE 'internal:sidebar-[a-z]+' | sort -u
```

在 1.18.30 上输出 6 个。注意其中 `internal:sidebar-footer` 属于 `sidebar_footer` slot，**不参与** `sidebar_content` 的排序，看 order 时忽略它。

**order 的数值解不出来。** 二进制里 id 被赋给了压缩后的变量名（`kD0="internal:sidebar-lsp"` 这种形态），`order` 写在别处的注册调用里，要跟踪变量引用才能配对——那是反编译级别的活，不是一条 grep。

实际可行的办法是**从渲染结果反推**：在 TUI 里把你的 `order` 调几个值，看额度小节落在哪两个内置小节之间，二分几次就定位了。起点参考上面那张 1.18.30 的表。

## 3. 标题带感叹号

`OpenCode Go !` 意思是**上次刷新失败了，你看到的是上一次成功的数值**。这是刻意行为：额度是慢变量，显示 5 分钟前的值比闪成空白有用。

跑诊断命令看 `message`：

| message | 含义 | 修法 |
|---|---|---|
| 含 `ECONNRESET` / `fetch failed` / `ENOTFOUND` | 网络问题 | 检查网络、代理、DNS |
| 含 `aborted` / `AbortError` | 15 秒超时 | 网络慢或上游卡住。等下次刷新 |
| `HTTP 500` / `502` / `503` | 上游故障 | 等，会自己恢复 |
| `响应缺少 usage 字段` | 上游响应格式变了 | 上游改了 API。对照 [配置与行为契约 §1](配置与行为契约_20260916.md#1-数据源) 的结构核对 curl 返回 |

感叹号会在下一次成功刷新后自动消失（`session.idle` 或 5 分钟兜底）。不需要重启。

如果感叹号**一直不消失**且诊断命令正常，那是渲染层没收到更新，看 [§5](#5-数字永久不更新)。

## 4. 百分比没有右对齐

期望是百分比贴侧栏右边缘：

```
5 小时用量             8%
```

如果看到的是紧跟标签：

```
5 小时用量   8%
```

说明 flex 弹性间隔没生效。把 `tui.tsx` 的 `UsageRow` 里这一行：

```tsx
<box flexGrow={1} />
```

换成：

```tsx
<box style={{ flexGrow: 1 }} />
```

重启 opencode。

> `formatPercent` 的 `padStart(4)` 在 flex 布局下是视觉空操作——那几个空格落在数字左侧，被弹性间隔吸收了。右对齐完全靠 `flexGrow`，不是靠 padding。

## 5. 数字永久不更新

先确认它**真的**不更新：额度只在助手消耗配额后才变，5 小时窗口在你不用的时候本来就不动。发一条消息让助手回复完，等几秒再看。

如果确实卡住：

| 检查 | 命令 / 方法 | 含义 |
|---|---|---|
| 数据层是否还活着 | 跑诊断命令 | 正常 = 问题在插件内部状态 |
| 是否命中了 `dead` 闩锁 | 诊断命令返回 `dead` | 换密钥后必须**重启** |
| 倒计时分钟数是否在走 | 等 60 秒看 | 倒计时走但百分比不动 = 刷新没触发；两者都不动 = 渲染层冻结 |

刷新触发源有三个（详见 [配置与行为契约 §6](配置与行为契约_20260916.md#6-刷新触发)）：启动时一次、每次 `session.idle`（20 秒节流）、5 分钟兜底。所以**最长 5 分钟内必须有一次刷新**。超过 5 分钟百分比完全不动、且诊断命令正常 = 插件内部状态卡住，重启 opencode。

> 历史上有一条真实的永久冻结路径：15 秒超时原本只覆盖响应头，`response.json()` 无保护，body 挂住就会让单飞标志永久为真、此后所有刷新被挡死。已修（超时现在覆盖到 body 读取完成）。如果你在 `6f0faf5` 之前的版本上，升级。

## 6. 百分比和 web dashboard 不一致

**这不是 bug。** opencode 官方 web dashboard 显示一位小数（`8.1%` / `53.4%` / `26.7%`），插件显示整数（`8%` / `53%` / `27%`）。

`/zen/go/v1/usage` 这个端点返回的 `percent` 就是**向下取整的整数**，web dashboard 走的是另一条更精细的通路。插件取不到小数位，这是数据源的硬限制，不是渲染问题。

同理，端点不返回 token 数或金额绝对值，所以插件做不了"还剩多少 token"。

验证：

```bash
KEY=$(python3 -c "import json,pathlib;print(json.loads(pathlib.Path.home().joinpath('.local/share/opencode/auth.json').read_text())['opencode-go']['key'])")
curl -s -H "authorization: Bearer $KEY" https://opencode.ai/zen/go/v1/usage | python3 -m json.tool
```

返回里的 `percent` 都是整数。

## 7. 倒计时显示"重置时间未知"

说明 `resetsAt` 不是可解析的时间串。上游返回格式变了。

```bash
KEY=$(python3 -c "import json,pathlib;print(json.loads(pathlib.Path.home().joinpath('.local/share/opencode/auth.json').read_text())['opencode-go']['key'])")
curl -s -H "authorization: Bearer $KEY" https://opencode.ai/zen/go/v1/usage | python3 -c "
import json,sys
for k,v in json.load(sys.stdin)['usage'].items():
    print(k, repr(v.get('resetsAt')))
"
```

期望是 ISO 8601 串，如 `'2026-09-21T00:00:00.724Z'`。

如果看到 `即将重置` 而不是"未知"，那是 `resetsAt` 已经过期（差值 ≤ 0），会在上游下次返回新时刻后自动恢复，不是故障。

## 8. `bun install` 或 `tsc` 失败

**`bun` 没装：**

```bash
bun --version
```

需要 bun（本项目在 1.3.14 上验证）。装它：`curl -fsSL https://bun.sh/install | bash`。

**`tsc` 报 `<box>` / `<text>` 的 JSX 元素隐式 any：**

说明 `@opentui/core` 的 JSX 命名空间没被加载。在 `tsconfig.json` 的 `compilerOptions.types` 里补上 `"@opentui/core"`：

```jsonc
{
  "compilerOptions": {
    "types": ["bun", "@opentui/core"]
  }
}
```

**依赖装了但运行时报找不到模块：**

不会发生，但值得知道原因：opencode 的插件加载器有一张 bare specifier 映射表，会把插件里的 `solid-js` / `@opentui/solid` 解析到**宿主自己的**运行时。本地 `node_modules` 纯粹是给 `tsc` 用的。这也顺带排除了"两份 Solid 导致响应式失联"的隐患。

**测试失败：**

```bash
bun test
```

期望 41 pass / 0 fail。如果有失败，对照 [配置与行为契约 §9](配置与行为契约_20260916.md#9-测试覆盖) 的覆盖表定位是哪一块。

## 完全卸载

```bash
rm ~/.config/opencode/tui.json
```

重启 opencode。你原有的 `opencode.json` / `opencode.jsonc` 从未被本插件改动过。

如果 `tui.json` 里还注册了别的 TUI 插件，只从 `plugin` 数组里删掉本插件那一项，别删整个文件。
